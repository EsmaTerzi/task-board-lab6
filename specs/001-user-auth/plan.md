# Implementation Plan: User Authentication System

**Branch**: `001-user-auth` | **Date**: 2026-05-12 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/001-user-auth/spec.md`

---

## Summary

Build a stateless JWT-based authentication system on top of Express.js + TypeScript + PostgreSQL. The system covers user registration, login, password reset via email, and 24-hour session expiry with explicit logout support via a JWT blocklist.

---

## Technical Context

**Language/Version**: TypeScript ≥ 5.0 (`strict: true`)
**Runtime**: Node.js LTS (22.x)
**Framework**: Express.js 4.x
**Primary Dependencies**:
- `bcrypt` — password hashing (cost factor 12)
- `jsonwebtoken` — JWT signing & verification (HS256)
- `pg` / `postgres` — PostgreSQL client
- `zod` — input validation at API boundary
- `nodemailer` — email delivery abstraction (SMTP)
- `dotenv` — environment variable loading

**Storage**: PostgreSQL 16 — tables: `users`, `password_reset_tokens`, `token_blocklist`
**Testing**: Jest + `ts-jest` + `supertest` (integration)
**Target Platform**: Linux server (Node.js process)
**Project Type**: Web service (REST API)
**Performance Goals**: Registration p95 < 3 s; Login p95 < 500 ms (bcrypt-bound)
**Constraints**: bcrypt cost ≥ 12; JWT secret ≥ 256-bit from env; no `any` types; ≥ 80% coverage on services
**Scale/Scope**: Single-region v1; single Node.js instance; in-process blocklist acceptable for v1

## Data Model

### `users`

| Column | Type | Constraints |
|--------|------|-------------|
| `id` | `UUID` | PK, default `gen_random_uuid()` |
| `email` | `VARCHAR(255)` | UNIQUE, NOT NULL, lowercase |
| `password_hash` | `TEXT` | NOT NULL |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, default `now()` |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL, default `now()` |

### `password_reset_tokens`

| Column | Type | Constraints |
|--------|------|-------------|
| `id` | `UUID` | PK, default `gen_random_uuid()` |
| `user_id` | `UUID` | FK → `users.id`, NOT NULL |
| `token_hash` | `TEXT` | NOT NULL (SHA-256 of raw token) |
| `expires_at` | `TIMESTAMPTZ` | NOT NULL |
| `used_at` | `TIMESTAMPTZ` | NULL until consumed |

### `token_blocklist`

| Column | Type | Constraints |
|--------|------|-------------|
| `jti` | `TEXT` | PK |
| `expires_at` | `TIMESTAMPTZ` | NOT NULL (for periodic cleanup) |

## API Contracts

### `POST /auth/register`
**Request**: `{ email: string, password: string }`
**Response 201**: `{ id: string }`
**Errors**: 400 (validation), 409 (duplicate email)

### `POST /auth/login`
**Request**: `{ email: string, password: string }`
**Response 200**: `{ accessToken: string }`
**Errors**: 400 (validation), 401 (invalid credentials)

### `POST /auth/logout`
**Headers**: `Authorization: Bearer <token>`
**Response 204**: _(no body)_
**Errors**: 401 (missing/invalid token)

### `POST /auth/password-reset/request`
**Request**: `{ email: string }`
**Response 200**: `{ message: "If this email is registered, a reset link has been sent." }`

### `POST /auth/password-reset/confirm`
**Request**: `{ token: string, newPassword: string }`
**Response 200**: `{ message: "Password updated successfully." }`
**Errors**: 400 (invalid/expired/used token, weak password)

## Key Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| JWT algorithm | HS256 | Single service, shared secret sufficient for v1 |
| Blocklist storage | PostgreSQL `token_blocklist` | Consistent with existing DB; Redis upgrade path available |
| Reset token format | `crypto.randomBytes(32)` → hex string | 256-bit entropy; SHA-256 stored in DB |
| Email sending | Synchronous in request cycle | Simplicity for v1; 503 on SMTP failure (documented) |
| Refresh tokens | Out of scope | v1 constraint; 24h access token accepted |
| Input validation | Zod at controller boundary | Type-safe, composable, `unknown` input → typed output |
